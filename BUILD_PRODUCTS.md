# Build NoeEngine for Linux, Windows, macOS and Android

`build.sh` builds **real native binaries** from this Godot-derived source tree. It never renames an incompatible binary into a different OS format. The build fails if required SDKs are missing or if the native compiler/package builder fails.

## No-argument full build

Calling **`./build.sh` without arguments** now runs the following four independent commands, strictly in order:

```sh
./build.sh check
./build.sh linux 2 --install-deps
./build.sh windows 2 --install-deps
./build.sh android 2 --install-deps
```

The pipeline is fail-fast. It never claims all builds passed if any stage fails, and the artifacts already produced by earlier successful stages remain in `Products/`. Because each stage uses `--install-deps`, it may download large SDK/compiler packages, use `sudo`, prompt for Android SDK licenses, and consume tens of gigabytes. On low-memory machines, retain the default **two compiler jobs**. The macOS installer remains an explicit macOS-host build (`./build.sh macos 2`) because it requires Xcode.

## Windows one-command native build

From an ordinary **Windows 10/11 x64** checkout, launch `build.bat` (or
`build.bat 2` to use two compile jobs). It runs
`misc/setup_windows_build.ps1` under Windows PowerShell 5.1 and verifies
the source tree first. The bootstrap checks Python 3.9+, pip, SCons 4.8.1,
**MSYS2 UCRT64 MinGW-w64 GCC/G++/windres**, plus NSIS. There is no Visual
Studio, MSVC, or standalone Windows SDK requirement for this build.
The bootstrap uses WinGet for MSYS2, Python, and NSIS; then uses signed MSYS2
`pacman` packages for the GCC toolchain. Package downloads require internet
access and installation permission. It never downloads or executes arbitrary
remote PowerShell scripts.

To check an existing compiler setup **without installing anything**:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File misc/setup_windows_build.ps1 -CheckOnly -SkipInstall
```

The native Windows build always passes `use_mingw=yes` to SCons,
even when Visual Studio is installed. The default `build.bat 2` uses two
compiler jobs, prints errors directly, and saves a timestamped full transcript
under `Products/logs/windows-mingw-*.log`. If the batch is double-clicked,
errors keep the window open using `pause`. Automation can set
`NOEENGINE_NO_PAUSE=1` to suppress that pause. An alternative MSYS2 root can
be set through `NOEENGINE_MSYS2_ROOT`.

### MSYS2 first-install recovery and build errors

On a fresh MSYS2 installation, updating `msys2-runtime` may deliberately
close the MSYS2 shell. The PowerShell bootstrap now answers that **specific**
runtime-upgrade confirmation and runs each full `pacman -Syuu` pass in a
fresh MSYS2 process. It does not suppress unrelated package errors, and the
process may be restarted up to four times before reporting a failure.

Compiler output from GCC, SCons and `windres` is displayed **as it happens**
and captured in `Products/logs/windows-mingw-*.log`. Errors are red,
warnings yellow, with failed native exit codes propagated back to
`build.bat`; the window pauses on failure (unless
`NOEENGINE_NO_PAUSE=1`). MSYS2 UCRT64 supplies the resource compiler as
`ucrt64/bin/windres.exe`, which is used for native Windows builds;
target-prefixed `windres` remains required for Linux cross builds.

If a compiler diagnostic appears, the last meaningful error **above** the
final `BUILD FAILED` banner identifies the failing source/tool. Running
`build.bat 2` again is safe and resumes already-installed packages and
incrementally compiled SCons object files.

A native Windows x64 editor and the installer must be generated by the real
SCons/package build before `Products/NoeEngine-setup.exe` is reported as
successful. The helper preserves existing process PATH overrides so CI's
selected Python and Developer Shell tools are not replaced by a different
system Python. GCC toolchain and installer downloads require network
access and disk space; the bootstrap does not bypass corporate
machine policies or software-installation permissions.

## MSYS2 damaged package database recovery

If MSYS2 displays `could not open file /var/lib/pacman/local/.../desc`,
the error is a missing local installed-package record, not a download mirror
failure. `build.bat` invokes `misc/msys2_pacman_health.sh` before resolving
packages and again after upgrading the MSYS2 runtime. It saves a complete
backup of `/var/lib/pacman/local` before any attempted repair, and only uses
`pacman -U --dbonly` with a **matching cached package archive**. It never
silently deletes package records or overwrites unknown installed packages.
When the matching archive is unavailable or the repair fails, the build
stops and prints the backup path for manual MSYS2 repair or reinstall.

## Source header policy

`misc/compact_godot_headers.py --apply` changes the recognizable long
standard Godot MIT banner in tracked C/C++ engine files to a concise SPDX MIT
tag and original upstream **copyright lines**. It does not rewrite third-party
license headers or revoke inherited rights. `LICENSE.txt`, `COPYRIGHT.txt`,
`NOTICE.md`, and `AUTHORS.md` retain the full attribution. The one-time
GitHub Actions migration runs the script and commits eligible source updates
only if the main branch has not advanced concurrently.

## Build matrix

| Command | Supported host | `Products/` output |
| --- | --- | --- |
| `./build.sh linux 2` | Linux | `NoeEngine.AppDir/AppRun` and `NoeEngine-linux-x86_64.tar.gz`; optional `NoeEngine-setup.deb` |
| `./build.sh windows 2` | Linux with MinGW-w64 and NSIS, or native Windows | `NoeEngine-setup.exe` |
| `./build.sh macos 2` | **Mac with Xcode** | `NoeEngine-setup.pkg`, containing `NoeEngine.app` |
| `./build.sh android 2` | Linux/macOS with SDK, NDK and JDK 17 | `NoeEngine-android-arm64.apk` (actual Android editor) |
| `./build.sh all 2` | Linux: Linux/Windows/Android. Mac: macOS/Android | Available native/cross-compiled outputs only |
| `./build.sh check` | Source checkout | Static/preflight checks, no native C++ compilation |
| `./build.sh patch-tools` | Go 1.23+ | `noe-updater` and `noe-patch-sign` |
 
Two compiler jobs (`2`) suit low-RAM machines. Native builds may take hours, tens of GB, and an internet connection for dependencies.

## Install dependencies automatically (opt-in)

```sh
./build.sh linux 2 --install-deps
./build.sh windows 2 --install-deps
./build.sh android 2 --install-deps
./build.sh macos 2 --install-deps  # Mac only, requires Xcode already installed
```

`--install-deps` authorizes package downloads and potentially sudo actions. On apt-based Linux it uses the configured operating-system repositories for compilers, SCons, MinGW-w64, NSIS, JDK and native headers. For Android, it downloads Google's command-line ZIP **only** from the documented official host and verifies the published SHA-256 before extracting it into a local SDK. `sdkmanager` installs Android platform 35, build tools 35, CMake and NDK r28b, and prompts for license acceptance when required. No downloaded shell scripts are executed.

If your OS does not support an automatic package setup, `build.sh` reports what needs manual installation. macOS Xcode/SDK must be installed through Apple tooling and cannot be fetched or legally bootstrapped on Linux by this script.

On Linux the `all` target will **fail** if either Windows or Android cross-build dependencies are unavailable. Run individual targets to build only what your machine supports.

## Install and run

- **Linux:** extract `NoeEngine-linux-x86_64.tar.gz` and run `NoeEngine.AppDir/AppRun` directly. The AppDir contains a real editor binary, launcher, icon and license notices. It is a portable archive, **not** a fully statically linked AppImage, so system libraries may still be required. On Debian/antiX, the optional `.deb` may also be installed normally.
- **Windows:** run `NoeEngine-setup.exe`. NSIS provides the installation/uninstallation flow. This is not an MSIX package; test it on real Windows.
- **macOS:** install `NoeEngine-setup.pkg`. It contains `NoeEngine.app`. Code signing/notarization is not provided. macOS setup must run on a Mac with Xcode and `pkgbuild`.
- **Android:** install the arm64 Android editor APK after enabling allowed sideloading on the test device. The APK is built with SCons/Gradle and checked for `AndroidManifest.xml`. It is not an Android export template or renamed desktop executable. Production signing, security review, and touch UX validation are still required.

## Code, icons, and runtime tests

The native editor uses `module_noqeri_enabled=yes`. Source Noqeri features remain a restricted subset; see `modules/noqeri/README.md` and `modules/noqeri/compatibility.json`. Godot upstream source attribution and license notices are preserved.

The files `icon.png`, `icon_outlined.png`, `icon.svg`, and `icon_outlined.svg` use the newly supplied NoeEngine cobra. Because the source was a PNG, the SVG wrappers are self-contained **raster-embedded SVGs**, not vectorized paths. Test their appearance in the editor and at high DPI before shipping.

`./build.sh check` runs Python tests and shell checks and is **not evidence of a successful C++ compile**. A release must still:

1. Compile with the target toolchain and inspect the logs in `Products/build-*.log`.
2. Run the Linux editor smoke tests (version, headless editor and Noqeri scene). On Windows/macOS/Android, manually start the produced app and test UI/interaction.
3. Verify setup/install and clean uninstall, code-signing where relevant, and update rollback after failed patches.
4. Test two-account Convex collaboration and Supabase realtime update notifications against dedicated, deployed NoeEngine backends before claiming those cloud features work.

No generated `Products` binaries are committed to this repository. Running the build locally creates those artifacts; GitHub commits are source only.
